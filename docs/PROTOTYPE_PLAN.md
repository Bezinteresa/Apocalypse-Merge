# Apocalypse Merge — план создания прототипа

Версия 0.4 · 21 октября 2026 года.

Цель первого результата: проверить, приятно ли объединять постапокалиптические вещи и достаточно ли мотивирует восстановление торговой точки. Код начат 22 октября 2026 года: отмеченные пункты реализованы и проверены.

**Подтверждённый приоритет:** механики → проверка рабочего цикла → визуальное оформление. На техническом этапе используются простые формы, подписи и номера. Новые объекты на поверхности сверх уже намеченных зон остаются идеями для будущего после проверки первых зон.

Ближайший порядок реализации:

1. Поле, определения предметов и цепочек, генераторы, перемещение и объединение.
2. Склад, заказы, деньги, расход предметов и проекты восстановления.
3. Сохранение и загрузка, затем энергия и обучение.
4. Проверка полного цикла на условной графике и исправление ошибок.
5. После ядра — отдельный функциональный тест сундуков, осколков, сборки карт и альбома на условных карточках.
6. Визуальное оформление проверенных механик и первой зоны. Гаражная глава, нижние этажи и социальная система расширяются отдельными этапами.

Для перехода к визуалу не требуется сначала реализовать все будущие этажи и социальные функции. Но оформление не подменяет проверку готовности основных действий, сохранений и прогресса.

## 2. Минимальные технические проверки

| Область | Проверяемое поведение |
| --- | --- |
| Мердж | Только одинаковая цепочка и уровень; правильный следующий ID; максимальный уровень не объединяется |
| Заполненное поле | Отказ выдачи не списывает энергию; перемещения и объединения остаются доступны |
| Заказы | Предметы и деньги меняются одновременно; повторная сдача не создаёт награду |
| Проекты | Соблюдаются зависимости; ресурсы и разблокировки меняются один раз |
| Новый генератор | Сохраняется во входящем хранилище; связанные заказы ждут размещения |
| Сохранение | Возврат после перезапуска сохраняет вещи, прогресс и шаг обучения |
| Повреждённое сохранение | Загружается предыдущая корректная копия; игрок получает понятное сообщение |
| Энергия | Нет начисления за отрицательное время; бонус выше лимита не теряется |
| Продажа | Защищены генераторы; отмена последней продажи возвращает вещь и списывает выручку |
| Контент | Все ID существуют; граф цепочек без циклов; требования достижимы по открытиям |

Для правил мерджа, сдачи, ремонта и расчёта энергии полезны автоматические проверки на чистом состоянии. Анимации, читаемость и удобство касания проверяются вручную. Не нужно покрывать тестами каждую кнопку только ради количества тестов.

## 3. Что измерять в первом тесте

| Событие / показатель | Зачем |
| --- | --- |
| Старт и завершение обучения | Найти первый непонятный шаг |
| Первый merge / O01 / R01 | Измерить скорость освоения и первой награды |
| Выдачи по генератору и номеру заказа | Оценить реальную стоимость цели |
| Попытка выдачи без места | Найти перегрузку поля |
| Попытка выдачи без энергии | Понять, где ожидание прерывает цикл |
| Продажа / отмена продажи | Увидеть нехватку места и ошибки |
| Завершение проекта | Измерить промежутки между изменениями магазина |
| Закрытие приложения и возврат | Проверить сохранения и причины остановки |
| Завершение R08 | Оценить длину главы и желание продолжать |

Для наблюдаемого теста достаточно локального журнала без персональных данных. Платформенную аналитику выбираем перед публикацией.

Рабочие цели: первое восстановление за 3–5 минут; игрок может объяснить, откуда получить предмет; после изменения магазина понимает следующую цель. Общая длина 15–30 минут — гипотеза для содержательного прототипа, а не требование искусственно замедлять игрока.

## 4. Вопросы после сессии

1. Что хотелось сделать следующим и почему?
2. Какие предметы было трудно различить или связать в цепочку?
3. Понятно ли, чем заказы отличаются от ремонта?
4. Возникал ли момент, когда казалось, что продолжить невозможно?
5. Какое восстановление было самым заметным?
6. Хочется ли открыть следующего посетителя или увидеть следующий объект?

По ответам отдельно оцениваем мердж, понятность целей и ценность изменений магазина. Если поле приятно само по себе, но ремонт не замечают, нужно усилить представление результата.

## 5. Границы прототипа

В первый прототип не входят сетевые функции, боевой режим, управление машиной, открытый мир, свободная застройка города, фракционная репутация, голод, жажда, износ, несколько игровых полей, сезонный пропуск, магазин платежей и сложные рекламные сценарии.

Многоэтажное убежище и социальные рейтинги входят в согласованное направление развития игры, но реализуются после проверки первой главы. Следующая последовательность и критерии описаны в разделе 8. Отдельное поле соревнования не является изменением объёма первого прототипа.

Любую новую идею сначала записываем как расширение. Включаем её в текущий этап, только если она нужна для проверки основного цикла или исправляет обнаруженную проблему.

### Проверки коллекций

Проверяем границы вероятностей, разные наборы и счётчики, гарант на 50-й выдаче и его сброс, достижение порога карты посреди открытия, обработку оставшихся выдач того же сундука как излишков, отказ обмена на готовую карту и однократность наград.

Перед утверждением частоты сундуков моделируем распределение сроков сборки: медиану, долгие случаи, последнюю недостающую карту и долю излишков. Фиксированное число обязательных полезных осколков не заменяет этот расчёт. Отдельно сравниваем варианты с обменом и без него, с гарантом и без него.

Сначала измеряем время до первой собранной карты, сундуки до первого полного набора и понятность обмена. Пример 2% легендарной редкости и шести осколков не становится финальным балансом только потому, что выглядит привычным.
