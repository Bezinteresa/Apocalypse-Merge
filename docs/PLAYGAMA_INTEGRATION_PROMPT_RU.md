### 3. Подключение SDK и сборка без проблем CSP

Для Яндекса предпочти самодостаточную поставку Bridge из npm, чтобы скрипт Bridge не требовал разрешения его CDN-домена. Официально предусмотрены npm и локальный режим Vite-плагина. [Инструкция установки](https://wiki.playgama.com/playgama/bridge-sdk/setup).

Пример для Vite, который нужно встроить в существующую конфигурацию, не стирая её плагины:

```js
import { defineConfig } from 'vite';
import playgamaBridge from '@playgama/bridge/vite';

export default defineConfig({
  base: './',
  plugins: [playgamaBridge({ mode: 'local' })],
});
```

В приложении используй `import bridge from '@playgama/bridge'` и дождись `bridge.initialize()` до обращения к функциональным API. В контрольной версии проверяется `bridge.isInitialized`, а не выдуманное `bridge.initialized`.

Проверь результат сборки, а не только исходный HTML:

- `index.html` действительно подключает локальный Bridge раньше игры.
- `playgama-bridge.js` присутствует в архиве; необходимые адаптеры не пытаются скачиваться с заблокированного CDN.
- `playgama-bridge-config.json` доступен рядом с `index.html`. Если сборщик его не переносит, добавь явное копирование/генерацию; одного файла в корне исходников недостаточно.
- В production HTML нет второго CDN-подключения Bridge или дублирующего SDK.
- Ресурсы открываются при размещении в подкаталоге; нет ссылок на localhost и файловые диски разработчика.
- Bridge остаётся владельцем инициализации SDK платформы. Не добавляй независимый второй `YaGames.init()` поверх работающего адаптера. Если нужны отсутствующие функции Яндекса, используй уже созданный экземпляр SDK через проверенный интерфейс адаптера, например `bridge.platform.sdk` в контрольной версии.

Скрипт Bridge в одну длинную строку обычно является нормальным минифицированным JS. Это не повод вручную переписывать или форматировать его. Не вставляй HTML страницы документации вместо содержимого JS; используй пакет и проверяй файл в Network.

Самодостаточный Bridge не отменяет загрузку официального SDK Яндекса и прочих разрешённых ресурсов. Собственные внешние хосты требуют отдельной проверки CSP. Не обещай, что локальный Bridge решает все сетевые ограничения. [Правила внешних хостов Яндекса](https://yandex.ru/dev/games/doc/ru/console/add-new-game).

### 4. Последовательность запуска, язык и Game Ready

Построй один понятный bootstrap:

1. Инициализировать Bridge и определить реальную платформу.
2. Сразу прочитать язык SDK и применить локализацию.
3. Настроить обработку пауз/звука с учётом начального состояния платформы.
4. Загрузить сохранения, проверить формат и выполнить миграции.
5. Восстановить незавершённые покупки; временная ошибка восстановления не должна создавать вечный экран загрузки. При необходимости запустить игру со статусом «покупка ожидает завершения» и повтором проверки.
6. Загрузить ресурсы первого экрана и показать работающее меню/обучение.
7. Убрать загрузочный экран, дождаться готовности ввода и отправить Game Ready один раз за запуск.

На старте прочитай `bridge.platform.language` после `initialize()`, а не только при открытии настроек. В адаптере Яндекса это должно обращаться к `ysdk.environment.i18n.lang`. Требование действует даже для игры с единственным языком. Нормализуй код и используй заявленный резервный язык, если перевод отсутствует. Не заявляй английский в консоли, если переведено только меню, а игровой контент остался русским. Проверь зелёный `I18N is used` в debug-панели с первого запуска. [Пункт 2.14 и методика проверки](https://yandex.ru/dev/games/doc/ru/requirements/2/14).

Контрольные соответствия сообщений JS Bridge и функций Яндекса:

| Через Bridge | Ожидаемый результат у Яндекса |
| --- | --- |
| `platform.sendMessage('game_ready')` | `features.LoadingAPI.ready()` |
| `platform.sendMessage('gameplay_started')` | `features.GameplayAPI.start()` |
| `platform.sendMessage('gameplay_stopped')` | `features.GameplayAPI.stop()` |

Проверь эти соответствия в выбранном адаптере. Game Ready нельзя отправлять сразу после загрузки SDK, пока ещё идёт загрузка или кнопки заблокированы fade-переходом. Gameplay start относится к реально начавшемуся/возобновлённому игровому процессу, stop — к его фактической остановке. Меню, победа, поражение, реклама и скрытая вкладка не должны считаться активной игрой. Не спамь одинаковые сообщения каждый кадр. [Разметка загрузки и геймплея Яндекса](https://yandex.ru/dev/games/doc/ru/sdk/sdk-game-events).

Если SDK не инициализировался в релизе на платформе, покажи понятную ошибку и повтор подключения. Не скрывай проблему бесконечной загрузкой или «успешным» mock-режимом. Локальная разработка без платформы может работать с явно обозначенным mock.

### 5. Единый контроллер паузы, времени и аудио

Создай один сервис жизненного цикла. Подпишись на `PAUSE_STATE_CHANGED` и `AUDIO_STATE_CHANGED` у `bridge.platform`; прочитай начальные `isPaused` и `isAudioEnabled`, если они предоставляются выбранной версией. Не жди первого события, чтобы учесть запрет звука. [Platform API Bridge](https://wiki.playgama.com/playgama/bridge-sdk/api/platform).

Проектная архитектура: храни независимые причины паузы, а не один флаг, который любой callback может сбросить:

```text
canRunGameplay = игровой экран активен
                 И нет меню/модального окна/ручной паузы
                 И нет платформенной паузы
                 И вкладка видима и имеет фокус
                 И нет активной полноэкранной рекламы

canPlayMusic = пользователь включил музыку
               И платформа разрешает звук
               И приложение видно и имеет фокус
               И нет блокирующей паузы/рекламы
```

Музыка в обычном меню допустима, если так задумано игрой; отсутствие активного геймплея само по себе не означает обязательную тишину во всех меню. Полноэкранная реклама, потеря фокуса и запрет звука платформой — другое дело.

Учитывай `visibilitychange`, `blur/focus`, `pagehide/pageshow` и события SDK. Основные платформенные события обрабатывай централизованно; дополнительные причины от рекламы добавляй только с понятным снятием причины при завершении/ошибке. Возврат фокуса не должен запускать бой поверх рекламы или открытого меню.

- Останавливай не только отрисовку: физику, AI, урон, спавн, игровые таймеры, комбо и ввод.
- Игровое время считай только в активном состоянии. Не сравнивай атаки с `Date.now()` так, чтобы за время паузы накопился урон.
- Для возврата из меню сохраняй оставшееся время до атаки. Не выдавай новый полный интервал при каждом открытии меню и не атакуй сразу за всю прошедшую паузу.
- Реальные cooldown и ежедневные задания отдели от игрового времени. По возможности используй серверное время; клиентские часы не дают надёжной защиты от накрутки. [Серверное время Яндекса](https://yandex.ru/dev/games/doc/ru/sdk/sdk-server-time).
- Выключай и музыку, и эффекты, включая отдельные HTMLAudio/Web Audio-источники, не управляемые аудиосистемой движка.
- После закрытия рекламы восстанавливай допустимое состояние, а не принудительно включай звук. Настройки «звук выкл.» и «музыка выкл.» должны сохраняться.
- Музыка запускается после допустимого действия пользователя; отказ autoplay не ломает игру. Не должно быть двух параллельных экземпляров трека после повторного входа в сцену.
- Подписки не должны дублироваться при каждом создании сцены; у временных слушателей нужна очистка.

### 6. Rewarded: подтверждение, выдача, ограничения

Проверяй поддержку через `bridge.advertisement.isRewardedSupported`. Для JS Bridge 2.x `showRewarded(placement)` не является обещанием успешного просмотра: результат отслеживается через `REWARDED_STATE_CHANGED`. Состояния включают `loading`, `opened`, `rewarded`, `closed`, `failed`; основание награды — только подтверждённый `rewarded`. [Rewarded API](https://wiki.playgama.com/playgama/bridge-sdk/api/advertisement/rewarded).

Требования к реализации в проекте:

- Просмотр запускается по явному нажатию на кнопку с точным описанием награды.
- Подпишись до вызова показа. Один запрос в работе; повторные клики и параллельный interstitial блокируются единым рекламным сервисом.
- Привяжи запрос к placement, выбранной награде и состоянию получателя. Ресурс должен попадать в постоянный инвентарь или корректно применяться к уровню; переход сцены не должен терять бонус.
- `opened`, обычное `closed`, ошибка, отмена, отсутствие SDK и mock не дают награду.
- Запоминай подтверждение просмотра и выдавай ровно один раз. Проверь реальный порядок событий адаптера: не потеряй `rewarded` из-за преждевременной очистки слушателя на соседнем событии закрытия.
- Раздели завершение просмотра и восстановление игры после рекламы. Награда не должна возобновлять бой до закрытия рекламного окна.
- Обработай выброс исключения, отказ SDK, отсутствие рекламы, повторные события и потерю связи. Ограниченное ожидание не должно превращаться в вечный busy или вечную паузу. Поздние события старого запроса не должны выдавать новый бонус или запускать игру поверх ещё открытой рекламы.
- Сначала надёжно зафиксируй результат, затем обновляй UI. Изменение ресурса и расход рекламного лимита не должны расходиться при сбое записи.

Если владелец не выбрал другой баланс, предложи общий лимит 3 успешные rewarded-награды, затем 3 часа перезарядки. Это наш вариант баланса, а не требование платформы. Лимит общий на все экраны и ресурсы; отмена его не расходует. Сохраняй счётчик и срок восстановления в облаке, показывай остаток и время ожидания. Обычный сброс игрового прогресса не должен обходить этот лимит. Объясни ограничения защиты без сервера.

### 7. Межуровневая реклама: не только функция, но и вызов

Реализуй `showInterstitial(placement)` с проверкой поддержки и обработкой `INTERSTITIAL_STATE_CHANGED`. Показывай в естественной паузе, а не во время ввода, боя, обучения или поверх другого рекламного/платёжного окна. `minimumDelayBetweenInterstitial` ограничивает запросы, но сам по себе ничего не показывает. [Interstitial API](https://wiki.playgama.com/playgama/bridge-sdk/api/advertisement/interstitial).

Обязательно подключи вызов к конкретному переходу между уровнями. Запрети повторный запуск от двойного нажатия «Дальше». Сохрани результат уровня до рекламного запроса. После `closed`/`failed` продолжи переход один раз; отсутствие рекламы не должно блокировать игру.

Если расписание не задано, предложи щадящий проектный вариант: не в обучении и первых уровнях, первый запрос не раньше 180 секунд после запуска, последующие — не чаще 120 секунд, только на границе уровней. Это предложение для согласования, не норматив Яндекса и не гарантия заполнения рекламой. Учитывай актуальные правила площадки и ограничения SDK.

В отчёте укажи: точку вызова, интервал, задержку первого показа, блокировки и результат теста. Не пиши «межуровневая реклама реализована», если есть только конфиг/обёртка без вызова из навигации.

### 8. Sticky-баннер и адаптивная компоновка

Проверяй `isBannerSupported`, вызывай реальный `showBanner`/`hideBanner` по политике проекта. Контрольная сигнатура JS: `showBanner('bottom', placement)`. По актуальной рекомендации Bridge баннеры размещаются на спокойных экранах и скрываются в активном геймплее; финальную политику согласуй с правилами конкретной площадки. [Banner API](https://wiki.playgama.com/playgama/bridge-sdk/api/advertisement/banner).

Нужны два варианта геометрии, а не одинаковая пустая полоса всегда:

- Если оболочка площадки уже уменьшает viewport под sticky, не вычитай высоту повторно. В нашем тесте Яндекс сам сдвигал/уменьшал доступную область; это наблюдение нужно перепроверить на новом размещении.
- Если реклама накладывается поверх игры, резервируй безопасную нижнюю область только под реально поддерживаемый/показанный баннер. Это было пожелание для будущих размещений, не утверждение об одинаковом поведении всех платформ.

Фон может доходить до низа, но кнопки, подсказки, важные подписи и зоны касания не должны попадать под рекламу. Не сжимай фон вместе с интерфейсом, если нужен полноэкранный фон. Учитывай resize, ориентацию, safe-area и фактические размеры. Не оставляй огромную пустую полосу там, где баннера нет. Один `div` под баннер не означает интеграцию рекламы.

Проверь отсутствие браузерного скроллбара и случайного swipe-to-refresh на игровом поле; собственную прокрутку карты/магазина сохрани. Важные элементы не должны обрезаться и перекрываться при повороте экрана. [Пункт 1.10](https://yandex.ru/dev/games/doc/ru/requirements/1/10).

### 9. Сохранение и загрузка

Основной интерфейс переносимого сохранения — `bridge.storage.get(...)` / `set(...)`. Загружай данные до старта игрового состояния и сохраняй значимые изменения. Один localStorage без синхронизации не является облаком. [Storage API Bridge](https://wiki.playgama.com/playgama/bridge-sdk/api/storage).

Для Яндекса прогресс должен переживать обновление страницы и смену ориентации; у игры с IAP необходимы облачные сохранения. Если используется особая механика фиксации прогресса, опиши её в комментарии разработчика. [Пункт 1.9](https://yandex.ru/dev/games/doc/ru/requirements/1/9).

Проектируй хранилище как единый сервис со следующими свойствами:

- Версия схемы, значения по умолчанию, проверка типов/границ, миграции старых сохранений без обнуления пользователя.
- В снимке — прогресс, заработанная и потраченная валюта, инвентарь, улучшения, текущий уровень/ход, здоровье, задания, настройки и данные восстановления платежей. Состав адаптируй к игре.
- Если есть локальный резерв, он является частью контролируемой синхронизации, а не вторым независимым источником правды. Изменения не должны обходить сервис и забывать поставить dirty.
- Ошибка/тайм-аут чтения облака не равна отсутствию сохранения. Не затирай неизвестное удалённое состояние пустым локальным. Предусмотри понятный повтор; покупки при неизвестном состоянии защищай от повторной выдачи.
- Не складывай целиком балансы и инвентарь локального и удалённого снимков. Явно выбери стратегию конфликтов. Время устройства и «последняя запись победила» не гарантируют правильность одновременных сессий.
- Объединяй частые изменения, не отправляй облачный запрос на каждую букву/кадр. После критического события инициируй сохранение сразу. Соблюдай лимиты площадки.
- Серийная очередь записей и ревизии: старый ответ не должен помечать более новое изменение сохранённым. Повтор после ошибки — с задержкой, без бесконечного спама.
- Уход со страницы не гарантирует завершения async-запроса. Не строй сохранение только на `beforeunload`/`pagehide`; восстанавливай недосинхронизированный резерв при следующем запуске.
- При наличии авторизации учитывай смену пользователя: не переноси платные данные одного аккаунта в другой. Гостевой режим и доступные ему возможности проверяются отдельно; не вызывай авторизацию без действия игрока.
- Сброс прогресса требует подтверждения и синхронизации с облаком. Не удаляй журнал уже выданных платежей, постоянные покупки и защищённые метаданные, иначе произойдёт повторная выдача или потеря прав.

Особенно важно для IAP: «Promise записи завершился» не всегда означает запись на сервер. Проверь fallback и очередь выбранного адаптера. У Яндекса `player.setData(data, true)` предназначен для немедленной отправки, а `flush: false` подтверждает постановку/валидность, не саму отправку. Используй существующий SDK Bridge, не второй `YaGames.init()`. Не плодить `getPlayer()` на каждый кадр — учитывай лимиты и переиспользуй подходящий экземпляр. [Семантика сохранений Яндекса](https://yandex.ru/dev/games/doc/ru/sdk/sdk-player).

### 10. Инап-покупки: каталог и пользовательский интерфейс

Товар задаётся в конфиге Bridge и регистрируется в консоли соответствующей платформы. Проверяй `bridge.payments.isSupported`; каталог получай через `getCatalog()`, покупку — `purchase(productId)`, список покупок — `getPurchases()`. В контрольной JS-версии `consumePurchase(productId)` принимает ID товара, а не токен нативного SDK Яндекса. Постоянные товары не консумируются. [Payments API Bridge](https://wiki.playgama.com/playgama/bridge-sdk/api/payments).

Не смешивай подпись нативного `ysdk.payments.consumePurchase(purchaseToken)` с внешним API Bridge. Формат квитанции и уникальный идентификатор транзакции проверяй отдельно для каждой целевой платформы.

- Лестницу цен и состав наборов согласуй с владельцем. Не зашивай в код фиктивные рублёвые ценники и «выгоду», которой нет.
- Цена и валюта на кнопке берутся из актуального каталога, а не из вручную заполненной таблицы. Состояния: загрузка, доступно, недоступно, покупка идёт, оплачено/ожидает выдачи.
- У Яндекса отдельно проверь получение обозначения и изображения портальной валюты из SDK. Если нормализованный каталог Bridge не предоставляет нужного поля/метода, дополни адаптер через уже инициализированный нативный SDK; не рисуй вместо этого фиксированную монету.
- Проверь Currency mock в debug-панели: после включения и перезагрузки должны меняться обозначение на TST и иконка на тестовую. Активные товары консоли должны соответствовать реально доступным товарам игры. [Проверка IAP и портальной валюты Яндекса](https://yandex.ru/dev/games/doc/ru/requirements/1/13).
- Отмена/ошибка оплаты не выдаёт ресурс. Не подменяй её «тестовой успешной покупкой» в релизе. Двойное нажатие не открывает несколько платежей.
- Когда кнопка покупки запускается из уровня, определи режим паузы и заблокируй конфликтующую рекламу.

### 11. Необработанные покупки — обязательный отдельный механизм

Bridge предоставляет API, но не знает экономику игры: что выдать, как сохранить результат и как не начислить повторно. Нельзя считать восстановление готовым только потому, что есть `purchase()`.

Разработай одну идемпотентную функцию обработки оплаченной транзакции для обычной покупки и восстановления. Рекомендуемый порядок:

```text
получить подтверждённую SDK квитанцию
→ проверить известный product ID и уникальный ID транзакции
→ проверить журнал уже выданных транзакций
→ если не выдавали: одной записью изменить инвентарь и отметить выдачу
→ дождаться подтверждённого серверного сохранения обоих изменений
→ для расходника вызвать consumePurchase с аргументом API Bridge
→ обновить статус/UI
```

На старте, после загрузки облака, проверь `getPurchases()` и обработай незавершённые расходники. Повторяй проверку до новой покупки и по кнопке повтора при временной ошибке. Для постоянных товаров восстанавливай право владения, а не выдавай бесконечно новый ресурс.

Обязательные свойства алгоритма:

- Один обработчик/очередь, без гонки фонового восстановления с новой покупкой.
- Уникальность по транзакции, не только по товару: один расходник можно купить много раз.
- Если запись награды не подтверждена сервером, не консумируй платёж и не показывай окончательный успех. Сохрани понятный статус ожидания.
- Если серверная запись удалась, а consume не удался, при повторе не начисляй заново: проверь журнал и повтори консумирование.
- Если приложение закрыли между выдачей и записью, после перезапуска восстановление должно привести к одной итоговой выдаче, а не нулю/двум.
- Не консумируй неизвестный товар или квитанцию без необходимой идентификации. Сообщи о несовпадении конфигурации, сохрани возможность разбора.
- Журнал выдач должен синхронизироваться между устройствами и переживать сброс прогресса. Продумай его рост в пределах лимита сохранений.
- LocalStorage сам по себе недостаточен для подтверждения оплаченного результата.
- Клиентская дедупликация не равна криптографической проверке квитанции и не решает атомарность нескольких устройств. Если нужен backend, реализуй серверную проверку и идемпотентную транзакцию; не заявляй о такой защите без сервера.

Выполни проверку Яндекса: оплатить тестовый товар, дождаться окна результата, обновить страницу, не нажимая «Хорошо», затем проверить выдачу и возможность следующей покупки расходника. Восстановление не должно зависеть от ручного нажатия «восстановить». [Методика консумирования Яндекса](https://yandex.ru/dev/games/doc/ru/requirements/1/13).

### 12. Лидерборд, если включён в задание

Создай конфигурацию точного технического имени и вызов отправки выбранной метрики. Разделяй «всего заработано» и «доступно для трат»: покупки за очки не должны уменьшать рекорд общего заработка. Отправляй корректное целое значение, учитывай направление сортировки и ошибки SDK; не блокируй игру из-за таблицы.

Наличие вызова отправки не означает наличия экрана лидерборда. Если нужен экран/авторизация, реализуй отдельно. [Leaderboards Bridge](https://wiki.playgama.com/playgama/bridge-sdk/api/leaderboards), [лидерборды Яндекса](https://yandex.ru/dev/games/doc/ru/sdk/sdk-leaderboard).

### 13. Ошибки прошлого проекта, которые нельзя повторить

Это история интеграции, а не список якобы полученных отказов по всем функциям.

| Что действительно произошло | Что требуется в новом проекте |
| --- | --- |
| Яндекс сообщил: SDK отсутствует или встроен некорректно, пункт 1.1 | Проверить загрузку и инициализацию реального SDK на площадке, не довольствоваться работающим localhost |
| В консоли браузера CSP заблокировала CDN `bridge.playgama.com` | Поставить пакет и локальный комплект Bridge; проверить весь production Network, не только заменить одну строку в HTML |
| Яндекс сообщил об отсутствии автоопределения языка, пункт 2.14, хотя игра была только русской | На старте реально прочитать язык через SDK, применить резервный ru и проверить I18N-индикатор |
| Враг продолжал отсчёт атаки при паузе, потере фокуса и уходе в меню; это нашли при тестировании | Останавливать игровое время и сохранять остаток интервала атаки, а не только выключать картинку/звук |
| Бонус rewarded перед уровнем вызывал сомнения в корректной выдаче | Проверить события SDK и фактическое применение бонуса после перехода; не считать это автоматически исправленным наличием кнопки |
| Был конфиг/обёртка interstitial и пустая область под sticky, но не было подключённых вызовов показа | Проверять функцию целиком: кнопка/переход → запрос → событие SDK → результат; отличать UI-резерв от баннера |
| Возник отдельный вопрос об обязательной проверке необработанных покупок | Реализовать восстановление и дедупликацию; не выдавать успешную тестовую покупку за доказательство всех аварийных сценариев |
| После переходов меню могли оставаться некликабельными | Убирать блокирующие overlay и сбрасывать флаги перехода при повторном входе; проверить цикл меню → настройки/магазин → назад несколько раз |

Известные замечания модерации здесь — SDK и язык. CSP — наблюдаемая техническая ошибка. Пауза, рекламные бонусы и UI — результаты/вопросы собственного тестирования. Не придумывай другие отказы Яндекса и не считай предварительную проверку гарантией окончательного одобрения.

### 14. Проверки перед выдачей готового результата

Сначала автоматические тесты сервисов, затем реальный черновик платформы. Моки полезны для аварийных сценариев, но не подтверждают реальную монетизацию.

Минимальная матрица:

1. Новый запуск/старое сохранение: SDK загрузился, язык прочитан на старте, Game Ready пришёл после готовности UI.
2. Меню → игра → победа/поражение → меню: корректные gameplay start/stop без лишних событий.
3. Blur, скрытие вкладки, платформенная пауза, меню: нет урона, ускоренных таймеров и звука; остаток атаки сохраняется.
4. Реклама + потеря фокуса + возврат: игра не возобновляется раньше закрытия рекламы; выключенная музыка сама не включается.
5. Rewarded: успешный просмотр, отмена, ошибка, нет рекламы, исключение, повторы событий, быстрые повторные клики, смена сцены.
6. Rewarded-лимит: общий для разных экранов, отмена не списывает попытку, cooldown переживает перезагрузку, повторный запуск и сброс прогресса.
7. Interstitial: вызов действительно подключён, первый показ и интервал соблюдаются, нет зависшего перехода при отсутствии рекламы.
8. Sticky: реальный показ/скрытие; маленький телефон, desktop, изменение размера; нет перекрытия кнопок и двойного резерва высоты.
9. Сохранения: перезагрузка, офлайн, задержка/ошибка чтения и записи, повтор, старый/повреждённый формат, сброс; облако не затирается при ошибке чтения.
10. Тот же аккаунт на втором устройстве: прогресс и платные права восстановились. Параллельные сессии — отдельно, с описанием ограничений.
11. Каждый зарегистрированный товар: верный состав, цена/валюта, успешная оплата, отмена и повторная покупка расходника.
12. Currency mock Яндекса: обновились обозначение и изображение валюты, а не только текст локальной кнопки.
13. Необработанный платёж: обновление до подтверждения окна результата; перезапуск до/после серверного сохранения, сбой consume, отсутствие повторной выдачи.
14. Повторный вход в сцены: UI кликабелен, нет дублирующихся слушателей, рекламы, музыки и таймеров.
15. Production-сборка: нет CSP/404/фатальных ошибок, все необходимые файлы в архиве, нет зависимости от dev-сервера.

Для черновика используй ссылку владельца вида `https://yandex.ru/games/app/ID?draft=true&debug-mode=16&lang=ru`; параметры и доступность сверяй с консолью. Проверяй индикаторы SDK, языка, Game Ready и игровые события; сохраняй краткий протокол реальных действий.

Тестировать платежи должен добавленный в консоли тестовый аккаунт с подтверждённым Яндекс-логином, а не просто отображаемым именем. Не проси пароль, код из SMS или платёжные реквизиты. Не совершай реальные списания ради проверки без явного согласия владельца.

### 15. Релизная упаковка и итоговый отчёт

Собери production, затем ZIP: содержимое выходной папки в корне архива, `index.html` не должен лежать внутри лишней папки. Включи Bridge, конфиг, игровые ассеты; не включай node_modules, секреты, исходные словари, старые билды, тесты и инструменты разработки.

Убери пользовательский доступ к dev-режиму, отладочной выдаче ресурсов, обходу оплаты и тестовому «успеху» рекламы. Если debug-код остаётся для разработки, изолируй его от релиза.

Оптимизируй медиа без порчи оригиналов. Догрузка музыки по требованию не уменьшает ZIP, если треки всё равно включены в архив. Перенос на внешний хост — отдельное решение с учётом доступности и CSP, не молчаливый обход ограничений.

Окончательный ответ должен содержать:

- Что изменено, где находятся сервисы и настройки.
- Версию Bridge, способ подключения и местонахождение конфига в сборке.
- Реальные точки показа рекламы, интервалы и лимиты наград.
- Состав сохраняемых данных, стратегию конфликтов и порядок восстановления покупок.
- Какие тесты пройдены локально, какие — в реальном черновике, а какие ещё не выполнялись.
- Путь к новому ZIP, дату сборки и размер; не выдавай старый архив за новый.
- Что нужно владельцу в консоли: товары/их активация, тестовый логин, облако, лидерборд, настройки баннера/CSP при необходимости.
- Остаточные риски и ограничения, без заявления «точно пройдёт модерацию».

Если доступа к реальному SDK/черновику/платежам нет, прямо укажи «не проверено на платформе». Наличие зелёных unit-тестов или одной успешной покупки не подтверждает все сценарии восстановления и модерационные требования.

Начни с краткого аудита проекта и списка недостающих данных. Затем внедряй интеграцию по разделам, сообщая о существенных решениях. Доведи до проверяемой сборки в пределах предоставленного доступа; не публикуй игру и не меняй коммерческие настройки чужой консоли без отдельного разрешения.
